# Hermes Agent Evaluation: Adopt, Fork, or Build

**Date:** 2026-08-30
**Evaluated:** `github.com/NousResearch/hermes-agent` @ `main` (v0.20.6 era), full source clone, ~6 months of git history fetched
**Compared against:** custom ~300-line Matrix bot (matrix-bot-sdk) + Claude Agent SDK `query()`, MCP-only tools, reaction approvals, Postgres job queue
**Binding constraint:** the agent touches money, home automation, and children's data

All citations are `path:line` in the hermes-agent repo unless otherwise noted. Claims marked **[unverified]** could not be confirmed from source.

---

## 1. Verdict

**Adopt — no fork — but only behind a hardened config that inverts its shipped defaults, validated by the two-week probe in §6.** Hermes is emphatically not a well-marketed thin wrapper: it is a large, defensively engineered system whose internals (approval plumbing, MCP client, cron durability, memory bounds, skill audit ledger) are substantially better than what you would build in a weekend, and it ships a real Matrix adapter with reaction-based approvals, optional E2EE, and per-room/per-user session isolation — plus a first-class Nix flake with a NixOS module. The catch is that its *shipped security posture is the opposite of your design*: shell executes as a bare host subprocess by default, the approval gate is a dangerous-pattern **blocklist** (default-allow) whose default mode lets an auxiliary **LLM auto-approve** flagged commands, MCP tool calls are ungated unless you opt each server into `trust: untrusted`, and the self-improving skills/memory system writes autonomously by default with its human-review gate off and undocumented in the example config. Every one of those is reversible with configuration — no code fork required — which is why the verdict is adopt rather than build. If the probe surfaces default-drift across upgrades or the approval UX doesn't hold up on a phone, fall back to the custom build; your design remains a rational, much smaller trusted computing base.

## 5. Blocking issues (and whether they block)

For a system touching finances, home automation, and children's data:

1. **Shipped defaults are default-allow with an LLM gatekeeper.** Unmatched shell commands run unprompted; matched ones are auto-approved by an auxiliary LLM (`approvals.mode: smart` is the shipped default, `hermes_cli/config_defaults.py:2530`); MCP writes are ungated (`trust: full` default). Running Hermes as shipped against your MCP fleet would be indefensible. **Not blocking — every element is config** (`mode: manual`, `trust: untrusted` per server, `approvals.deny`), but it is mandatory hardening, and you carry the risk that an upgrade changes a default. Pin the config explicitly (never rely on defaults) and pin versions via the flake.
2. **The agent process itself is unsandboxed by design.** Plugins, skills (Python at import time), MCP stdio servers, and hooks run with full agent privileges; the project states the OS is the only boundary (`SECURITY.md:58-65, 150-164`). **Not blocking for you** — you'd run it in a systemd-hardened unit or container with only HTTP egress to your MCP servers, and you have no need for the terminal toolset at all — but it means "don't install community skills/plugins" is a hard house rule, and the skills-hub ecosystem is off the table.
3. **Autonomous self-modification is on by default and eager** ("A pass that does nothing is a missed learning opportunity", `agent/background_review.py:621-623`), the human-review gate defaults off and is undocumented in the example config, and the gate **fails open** on import error (`tools/memory_tool.py:960-965`). Memory writes have **no audit ledger** (skills do). **Not blocking** — disable `background_review` + `curator`, or enable `write_approval` on both subsystems and put `~/.hermes/{memories,skills}` under git via your nix-config for the diffable history you want. But verify the gate is actually active during the probe (it fails open silently).
4. **No per-user authorization inside one agent.** Anyone on `MATRIX_ALLOWED_USERS` for a profile can invoke every tool that profile has; memory is shared. **Not blocking** — profiles-per-family-member is the supported isolation model and is *stronger* than your single-process design — but it means N bot accounts, N systemd services, N configs to keep coherent (your nix-config is exactly the right tool for that).
5. **Security track record cuts both ways.** Real 2026 CVEs including a CVSS 8.7 dashboard issue and an active exploitation campaign against misconfigured deployments (§3). Responses were fail-closed redesigns, and current defaults (loopback binds, mandatory API keys, no-op `--insecure`) are sound. **Not blocking, but budget for tracking releases**; a stale Hermes is a bigger risk than a stale 300-line bot.
6. **Update treadmill / default drift.** 300–650 PRs per weekly patch release. **The one issue with no config fix.** Mitigation: pin via flake input, read release notes for `config_defaults.py` diffs before bumping, and keep the probe's abandon criteria live permanently.

None of these individually disqualifies it; #6 is the one that would eventually send you back to the custom build if it bites.

## 5b. Fork delta

**A fork is not required.** The changes your threat model demands are configuration; the two genuine gaps have plugin-shaped (not fork-shaped) fixes:

| Change | Mechanism | Size |
|---|---|---|
| Human-only approvals | `approvals: {mode: manual, timeout: 300, cron_mode: deny}` in config.yaml | config |
| Gate all MCP writes | `mcp_servers.<name>.trust: untrusted` on every server; annotate read-only tools with `readOnlyHint: true` **in your own MCP servers** so reads don't prompt | config + small changes in your TS servers |
| Kill shell/filesystem tools | `platform_toolsets.matrix: [<list without terminal/file>]` (e.g. start from `safe` + skills/todo) and/or `agent.disabled_toolsets` | config |
| Kill autonomous self-modification | `auxiliary.background_review.enabled: false`, `curator.enabled: false` — or keep them and set `memory.write_approval: true`, `skills.write_approval: true` | config |
| Deny-list belt-and-braces | `approvals.deny` globs for anything unforgivable | config |
| Auditable memory/skills | Manage `~/.hermes/{memories,skills}` as a git worktree from nix-config; commit on a timer | ~20 lines of Nix/systemd |
| Per-user tool scoping in one room (if you ever want it without profiles) | Override `toolsets_for_source()` in a Matrix adapter subclass shipped as your own platform plugin (the hook exists; the webhook adapter already uses it) — `gateway/platforms/base.py:7423-7440` | ~50–150 lines, own plugin dir, zero core changes |
| Matrix MAS refresh tokens (only if you move to MAS) | Upstream issue #93929; adapter-local change | not needed for plain Synapse |

If you ever *did* need to change the approval engine itself (`tools/approval.py`, 5,802 lines, single module, "single source of truth") it is fork-hostile at this release velocity — that would be the moment to build instead.

## 6. Two-week probe plan

**Setup (day 1, all in nix-config):** package via their flake; one `hermes-test` profile as a NixOS/systemd service (hardened unit: `DynamicUser`, no home access beyond `HERMES_HOME`, IP allowlist to your Synapse + MCP hosts + model provider); dedicated Matrix bot user on your Synapse; two rooms (one plaintext, one E2EE, `MATRIX_ALLOWED_USERS` = you + spouse). Config: the full §5b hardening — `approvals.mode: manual`, all MCP servers `trust: untrusted`, `platform_toolsets` without terminal/file, `write_approval: true` on both subsystems, streaming left off, dashboard not enabled. Point it at 2–3 real MCP servers (home automation + one read-only finance view — not write-capable finance tools yet), several hundred tools total across them to exercise tool_search.

**Watch for (log/measure daily):**
1. **Approval UX on the phone**: does every write-capable MCP call actually produce a reaction prompt in Element; does requester-enforcement hold when your spouse reacts; do timeouts fail closed. Try to get one write through *without* a prompt (readOnlyHint lies, `tool_call` bridge, cron job) — any success is a finding.
2. **Gate liveness**: confirm `/skills pending` and `/memory pending` accumulate instead of direct writes (the gate fails open silently on import error). Diff `~/.hermes/{memories,skills}` in git daily.
3. **Tool discovery at scale**: does the model find the right tools via the BM25 bridge, or flail? Token cost per turn (listing tier it lands in), and whether raising `listing_max_tokens` is needed.
4. **Matrix stability**: token longevity on Synapse, E2EE room behavior across a bot restart (crypto.db/device ID persistence), thread/media handling, edit spam if you try streaming on.
5. **Cron**: one daily job delivering to a room; restart the service mid-window; confirm skip-not-double semantics and delivery into the E2EE room.
6. **Ops cost**: RSS/CPU of the gateway at idle and under a burst (the unverified number); upgrade one release mid-probe and diff `config_defaults.py` for default changes.

**Abandon (build the custom bot) if:** any write-capable MCP call executes without a human approval under the hardened config (bypass of the trust gate); a pending-write gate is silently inactive; a release upgrade changes an approval/trust/review default out from under you; Matrix E2EE or session state proves flaky across restarts in a way that costs you more than a day; or idle footprint per profile makes five family profiles unreasonable on your hardware. **Adopt fully if** two weeks pass with the gates holding, the pending queues manageable (a few items/day, not dozens), and tool retrieval working — then add the finance write tools, the spouse's profile, and kid profiles with narrowed `platform_toolsets`.

## Appendix: what your custom build would still have over Hermes

Honesty in the other direction: a ~300-line TS bot gives you a trusted computing base you can read in an afternoon, true default-deny (only your MCP servers exist; nothing else is even loadable), one language, no update treadmill, and Postgres-native state you already operate. What it does not give you — and what you would slowly rebuild — is everything in Q2/Q4/Q6 above: throttled edit streaming, reaction approval plumbing with requester enforcement, media/voice handling, E2EE session management, a reconnecting circuit-breakered MCP client, tool search at catalog scale, durable skip-not-queue cron with incident dedup, and bounded memory. That list is why the verdict is adopt-behind-hardening rather than build.
